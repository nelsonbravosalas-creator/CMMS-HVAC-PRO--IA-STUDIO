## Hallazgos

### R1 — El bootstrap reimpone la contraseña en cada deploy (confirmado por código)

`vercel-build` ejecuta `db:bootstrap` en cada deploy. Mientras existan `CMMS_BOOTSTRAP_ADMIN_EMAIL` y `CMMS_BOOTSTRAP_ADMIN_PIN` en Vercel, el `INSERT ... ON CONFLICT DO UPDATE` actualiza `pin_hash` a partir del PIN de la variable, y además revoca todas las sesiones activas de ese administrador. El commit cambió `DO NOTHING` por `DO UPDATE`; antes, el PIN solo se fijaba la primera vez.

**Impacto:** si el administrador cambió su PIN y las variables siguen definidas, el siguiente deploy restablece el PIN original y cierra su sesión.

### R2 — Un administrador bootstrap anterior queda activo (confirmado por código)

La consulta elige la fila del correo bootstrap, o la fila `BOOTSTRAP-ADMIN`, pero nunca desactiva las demás filas con perfil `administrador`. Si cambió el correo bootstrap, la cuenta anterior conserva su acceso.

### R3 — Toma de control de una cuenta existente (confirmado con BD simulada)

Si el correo bootstrap coincide con una cuenta ya existente (escenario probado: supervisor `USR-SUPERVISOR-1`), el `INSERT` reutiliza ese `uuid_sync` y lo convierte en `administrador` con PIN nuevo, `cliente_id = NULL`, borra sus `user_clientes` y revoca sus sesiones. Con la variable configurada, esto es una escalada de privilegios no intencionada.

Traza emitida (escenario r3):

```
SELECT uuid_sync FROM users WHERE uuid_sync = 'BOOTSTRAP-ADMIN' OR LOWER(correo) = LOWER(?) ...  -> USR-SUPERVISOR-1
INSERT INTO users (...) VALUES ('USR-SUPERVISOR-1', ..., 'administrador', ...) ON CONFLICT (uuid_sync) DO UPDATE ...
DELETE FROM user_clientes WHERE user_id = 'USR-SUPERVISOR-1'
UPDATE cmms_sessions SET revoked_at = ... WHERE user_id = 'USR-SUPERVISOR-1' AND revoked_at IS NULL
```

### R4 — Cambio de PIN obligatorio reactivado en cada deploy (confirmado por código)

`data.requiere_cambio_pin` se fija a `true` en cada ejecución (`parametric-seed.ts`, bloque `bootstrapData`). `api/auth.ts:104` lo devuelve y `src/context/AuthContext.tsx:251` fuerza el cambio. Efecto: el administrador debe volver a cambiar el PIN tras cada deploy mientras la variable exista. Se combina con R1.

### R5 — Validaciones previas (PASS)

Correo no local, PIN de 6 dígitos, bloqueo de usuarios demo en hosting y guard de administrador operativo antes de desactivar demos: presentes en el código y `check-production-safety.mjs` pasa.

### R6 — Compatibilidad con el simulador offline (no aplicable localmente)

El bloque de bootstrap solo se ejecuta con `VERCEL=1` o `NODE_ENV=production`. El modo simulado nunca lo ejecuta. El SQL es PostgreSQL estándar, pero **no se verificó contra una BD real**: pendiente con una instancia Neon de prueba.
